# 基准测试：Ternary Bonsai 2 27B 在 RTX 4090 上的吞吐

本文是一次**完整跑分**（`just bench <制品> all`，两个三元制品各 20 条用例）的记录：读数、口径、环境，
以及这些数字**能**用来下什么结论、**不能**用来下什么结论。

**本文不含困惑度（Perplexity）。** 这一项的位置已经在 §7 预留：引擎目前没有能产出 PPL 的通路，
硬凑一个数只会误导。那一节写清楚了缺什么、以什么口径补。

有一处**未解释的读数**必须写在最前面：PQ2_0 的 `pp+tg` 用例里，prefill 在约 255 t/s 与约 838 t/s
两个档位之间跳（逐次数据见 §6.1）。因此本文**不给出**那几行 prefill 的均值结论，只给档位证据与
尚未做完的归因实验清单。

## 1. 结论摘要

本机（RTX 4090 24 GB / 驱动 610.57.04 / CUDA 13.3），两个三元制品各 20 条用例、每条 5 次重复：

| 维度 | 结果 | 出处 |
|---|---|---|
| prefill（只取 `pp` 用例）| PQ2_0 **261 – 292 t/s**；PTQ1_0 **43.9 – 51.1 t/s** | §5.1 §5.2 |
| prefill（`pp+tg` 用例）| PQ2_0 **不可用**：逐次在 ~255 与 ~838 t/s 两档间跳，均值无意义 | §6.1 |
| decode | PQ2_0 **41.8 – 56.4 t/s**；PTQ1_0 **16.3 – 16.7 t/s** | §5.1 §5.2 |
| CUDA Graph | 关图后 PQ2_0 decode 44.7 → **22.1 t/s**、PTQ1_0 16.5 → **5.0 t/s**；prefill 不变 | §5.1 §5.2 |
| KV 精度/编码 | 六种 KV 格式对 decode 的影响在 ±20% 内；KV 载荷 8.5 – 41.9 MB（ctx 640）| §5.1 |
| MTP 投机 | 两个格式都**没有收益**：PQ2_0 off 48.2 → draft4 43.0 t/s，接受率 32.6% | §5.1 §5.2 |
| 显存 | 权重上传 PQ2_0 7.19 GB / PTQ1_0 5.93 GB；KV 载荷随上下文线性 | §5.4 |
| 跨格式 | PTQ1_0 的 prefill 是 PQ2_0 的 **~1/6**，decode 是 **~1/3**，换来省 1.26 GB 显存 | §5.3 |

一句话：**PQ2_0 的 decode 约 45 t/s、prefill 约 270 t/s（`pp` 口径）是本机能站住的量级；小数点后的
位数在本机上没有意义。要吞吐选 PQ2_0，PTQ1_0 买到的是更小的盘上体积与显存。**

## 3. 口径：这些数分别是什么

### 3.1 三个 test kind 的计时边界

`ninfer_bench` 走的是**产品路径**：`Engine::prepare_tokens()` + `Engine::generate()`，没有私有的
prefill/decode 循环。三种 kind 的定义（沿用上游 `bench/README.md`）：

| kind | 做什么 | 报什么 |
|---|---|---|
| `pp{P}` | 准备 `P` 个 token，只请求 1 个输出 token | prefill t/s = `P / GenerationTimings.prefill_seconds` |
| `tg{G}` | 在计时区间外准备 1 个 token 的种子，请求 `G+1` 个输出 token | 计入 decode 的正好是 `G` 个 token |
| `pp{P}+tg{G}` | 先 `P` token prefill，再按同样约定生成 `G+1` | 同一次生成里的两段速率 |

所有请求都用 raw 输出、关掉模型自带的停止条件、关掉前缀复用（`ninfer_bench.cpp` 里
`execution.allow_prefix_reuse = false`）—— 目的是让"请求了多少 token"是精确的，而不是再引入一条生成路径。

### 3.2 被钉死的量

`tools/bench/bench.sh` 把这些值固定下来，手敲很容易漏：`-r 5`（5 次重复）、`--warmup 1`（1 次预热，
不计入）、`--prefill-chunk 1024`、语料同上、CUDA Graph 默认开（`graph-off` 那条用例显式关）。
`max_context` 由每条用例的 token 数自动定容，表里逐行给出。

### 3.3 表里的数是什么统计量

**5 次重复的均值 ± 样本标准差**，`rsd` 列 = 标准差 / 均值。`rsd` 大（> 10%）的行请按 §6 的方式理解：
它们描述量级，不描述可复现的精确值。

### 3.4 四个容易读错的地方

1. **`pp512` 与 `pp512+tg128` 的 prefill 不是同一个量。** 前者只请求 1 个 token，后者后面还跟着 128 步
   decode，两段都参与同一次生成的墙钟。跨表比较时不要把它们当成同一个数。
2. **`pp+tg` 的 prefill 列在 PQ2_0 上有档位问题**（§6.1），只有 `pp` 列的 prefill 与所有 decode 列可用。
3. **`decode_output_tok_s` 与 `decode_engine_tok_s` 在本次运行里逐行相同**（含 MTP 三条）。上游文档说后者
   会带上最后未提交的投机轮工作，本机这一版读数里没有体现出来，照抄 CSV 即可，不要按上游文档想当然。
4. **进程内的历史会影响读数。** 同一条 `-pg 512,128` 在本文里出现 8 次（两个制品各 4 次），给出 8 个不同的
   prefill 数，原因见 §6。

## 4. 复现

```bash
# 需要 NINFER_ROOT=<ninfer 源码树>（同时用来定位语料）与 ninfer_bench 构建
just build-bench
just bench /data/Ternary-Bonsai-2-27B-ninfer/Ternary-Bonsai-2-27B-PQ2_0.ninfer all
```

`ninfer_bench` 由 `just build-bench` 构建（`-DNINFER_BUILD_BENCHMARKS=ON`）。输出目录：

```text
out/bench-<制品名>-<UTC 时间戳>/
  manifest.txt            环境与输入摘要（§2 的表就来自这里）
  results.csv             全部用例的 tidy CSV，首两列是 case,suite
  all__<case>.csv         单次 ninfer_bench 的原始 CSV
```

`out/` 是**证据目录**：脚本不写进制品目录，`just clean` 也刻意不删它。

三类可用读数的解读：

- **prefill 随长度平坦**（261 / 283 / 278 t/s，512 / 2048 / 8192 token）。`pp512` 略低是它每次只请求
  1 个 token、单次生成的固定开销占比更大。这三个数的 `rsd` ≤ 5%，是本文最稳的 prefill 结论。
- **CUDA Graph 只对 decode 有意义**：开图 44.7 t/s、关图 22.1 t/s（同一 `-pg 512,128`，`rsd` 均 ≤ 7%），
  prefill 两行 244.1 对 245.6 在噪声内相同。原因是 decode 每步只发一次小规模 kernel 序列，发射开销
  占比高；prefill 本来就长。
- **MTP 在 bench 口径下没有收益**：只比 decode 列，off 48.2 → draft4 43.0 t/s，接受率 32.6%。这与 CLI
  贪心口径的 74% 接受率不矛盾 —— 基准自己采样，且把草稿开销算进墙钟。`draft8` 那条显式关图是
  **规避上游缺陷**（草稿窗口 ≥ 8 时 CUDA Graph 的 exec update 会失败，官方非三元制品同样复现），
  它量的是缺陷，不是投机。

## 6. 噪声与档位：同样的命令为什么给出不同的数

这是本次跑分最值得记下来的一条，因为它决定了本文之外的所有对比应该有多保守。

### 6.1 证据一：同一个工作负载的八个读数

`-pg 512,128`（prefill 512 + 生成 128）在本文出现八次，参数只差自动定容的 `max_context`，prefill 的
计算量完全相同：

| 出现位置 | 制品 | max ctx | prefill t/s | rsd |
|---|---|---|---|---|
| `panel` | PQ2_0 | 2048 | 258.8 ± 19.0 | 7% |
| `kv-bf16` | PQ2_0 | 640 | 691.0 ± 233.5 | 34% |
| `mtp-off` | PQ2_0 | 640 | 344.6 ± 95.4 | 28% |
| `graph-on` | PQ2_0 | 640 | 244.1 ± 20.9 | 9% |
| `panel` | PTQ1_0 | 2048 | 44.3 ± 0.2 | 1% |
| `kv-bf16` | PTQ1_0 | 640 | 43.2 ± 0.7 | 2% |
| `mtp-off` | PTQ1_0 | 640 | 43.9 ± 0.7 | 1% |
| `graph-on` | PTQ1_0 | 640 | 41.9 ± 0.5 | 1% |

PQ2_0 的最高与最低相差 **2.8 倍**，PTQ1_0 只差 6%。同一台机器、同一个二进制、同一份语料。

### 6.2 证据二：逐次重复的读数显示两个档位

`results.csv` 只给均值，所以另跑了三次取逐次数据（`-o json`，把 `reps[]` 里每次重复的 `prefill_seconds`
换算成 t/s）。PQ2_0，`-pg 512,128`：

| 运行 | 参数 | 逐次 prefill t/s | 均值 |
|---|---|---|---|
| D1 | `-r 5 --warmup 1` | 258.4 260.8 258.1 204.2 299.8 | 256.3 |
| D2 | `-r 8 --warmup 3` | 267.5 468.9 263.1 394.0 238.7 **838.9 838.5** 270.6 | 447.5 |
| D3（`pp512+tg128`）| `-r 8 --warmup 3` | **837.4 837.6 837.6** 277.6 258.0 253.1 270.4 317.5 | 486.1 |
| D3（`pp512`，只有 prefill）| `-r 8 --warmup 3` | 278.6 313.1 287.5 299.9 258.6 300.1 278.7 183.1 | 275.0 |
| D3（`pp2048`）| `-r 8 --warmup 3` | 294.4 293.9 281.7 290.2 286.9 297.7 282.8 286.0 | 289.2 |

同一个进程里，prefill 会在两个档位之间跳：

- **快档 ≈ 838 t/s**，且**重复到小数点后两位**（837.4 / 837.6 / 837.6；838.9 / 838.5）。纯计算决定的量
  才会这样重现。
- **慢档 ≈ 255 – 317 t/s**，`rsd` 明显更大（±12%）。
- 中间值（394.0、468.9）也出现过，说明这不是"整次重复快或慢"的开关。
- 同一批运行里 decode 的表现完全不同：D3 的 `tg128` 八次是 47.0 57.6 59.2 63.3 51.7 51.9 51.3 49.9，
  是连续变化而不是两个孤立档位。**所以这不是"整卡快慢"，是 prefill 特有的现象。**

对照：PTQ1_0 同样的 `-pg 512,128`（§5.2 的四行）`rsd` ≤ 2%，没有档位。

### 6.3 与上一次跑分的对照

`tools/bench/README.md` 里记着更早一次运行的读数（不同时段、驱动同为 610.57.04）。同参数对照：

| 用例 | 上一次 | 本次 | 偏差 |
|---|---|---|---|
| panel pp512 | 267.2 ± 18.4 | 260.5 ± 16.2 | −2.5% |
| panel pp2048 | 303.4 ± 5.6 | 291.8 ± 6.7 | −3.8% |
| panel tg128 | 50.8 ± 4.3 | 49.9 ± 11.3 | −1.8% |
| kv bf16 prefill | 427 | 691.0 | **+62%** |

`rsd` 小的行（panel 全部）两次运行吻合在 4% 以内；带档位问题的 prefill 行差了 20% – 60%。
**"跑得快不快"看前一类，"跑得多快"不要看后一类。**

### 6.5 未完成的归因，与怎么把它做完

本文**没有**给出档位原因的结论。已经排除的与还没排除的：

| 假设 | 状态 |
|---|---|
| 前缀复用（复用了上一次重复的 KV，少算了工作量）| **源码层面已排除**：`ninfer_bench.cpp` 设了 `allow_prefix_reuse = false`。仍未做的是直接读引擎回报的 `GenerationResult.reused_prompt_tokens` / `prefix_reuse_path` —— 这两个字段没有进 bench 报告，补一行打印即可证伪 |
| MMA / SIMT 路径切换（`NINFER_TERNARY_MMA`）| **未测**：源码里该开关是 `static`（每进程只读一次），理论上不会逐次切换，但没有实测过 |
| prefill 分块数变化（`--prefill-chunk`）| **未测** |
| GPU 时钟 / 功耗墙 | **未对齐**：没有把 100 ms 采样的时钟序列与逐次边界对齐过 |

把它做完的命令（本机当时已不可用，见 §8）：

```bash
B=/data/ninfer-build-bench/bench/ninfer_bench
A=/data/Ternary-Bonsai-2-27B-ninfer/Ternary-Bonsai-2-27B-PQ2_0.ninfer
C=<ninfer 源码树>/bench/fixtures/bench_corpus.ids

# 1. 档位分布：20 次重复，看快档占比
"$B" --weights "$A" --corpus "$C" -pg 512,128 -r 20 --warmup 3 -o json --output-file /tmp/rep.json

# 2. 是不是 MMA/SIMT 切换
NINFER_TERNARY_MMA=0 "$B" --weights "$A" --corpus "$C" -pg 512,128 -r 8 --warmup 3 -o json --output-file /tmp/mma0.json
NINFER_TERNARY_MMA=1 "$B" --weights "$A" --corpus "$C" -pg 512,128 -r 8 --warmup 3 -o json --output-file /tmp/mma1.json

# 3. 是不是分块
"$B" --weights "$A" --corpus "$C" -pg 512,128 --prefill-chunk 128 -r 8 --warmup 3 -o json --output-file /tmp/chunk128.json

# 4. 时钟是否与档位对齐（另开一个终端，100 ms 采样）
nvidia-smi --query-gpu=clocks.sm,power.draw,temperature.gpu --format=csv -lms 100 > /tmp/clocks.csv
```

### 6.6 结论

- 本文件的表格里，`rsd` ≤ 10% 且不带 ‡ 的行可以当作同一台机器上的稳定读数；带 ‡ 的行只应当作量级。
- 跨机器、跨驱动、跨时段、跨 suite 顺序的比较，在**没有锁频、没有固定预热**的前提下不可靠。
- 想让某个数变成可引用的结论，做法是：单独跑一条用例、`-r` 提到 10 以上、`--warmup` 提到 2 以上，
  并把 GPU 状态（时钟/温度/功耗）一起记下来。

## 7. 困惑度（Perplexity）：待测

**本节的表全部是空的，这不是"未通过"，而是"还没测"。** 位置在这里预留，补上时不需要改动其它章节。

### 7.1 现在为什么是空的

| 事实 | 依据 |
|---|---|
| 本移植的验收判据是"逐字节一致 + 吞吐"，不含困惑度 | 移植报告、本文 §5 |
| `ninfer_bench` 只测吞吐，不产出任何似然量 | 上游 `bench/README.md`；本文引用的 CSV 列里没有 NLL/logits |
| 上游 `eval/` 是能力套件（AIME / GPQA / needle-in-haystack），不是 PPL | `eval/configs/*.yaml` |
| 公开路径 `Engine::generate()` 只回 token id，不回逐 token logprob | 引擎头文件；`ninfer-serve` 未开 `logprobs` |

### 7.2 补上它需要什么

1. **一条只读的似然通路**：给定一段 token id，返回每个位置的负对数似然（NLL）。最自然的位置是
   `Engine` 上加一个 `score_tokens()`（复用现有的前向与 KV 布局，不新建生成路径），或在
   `ninfer-serve` 上开 `logprobs` 再写一个打分脚本。二者都要保证打分走的是与生成完全相同的算子路径，
   否则量到的是另一套东西。
2. **钉死语料与 tokenizer**：数据集、分词器、是否加 BOS、窗口边界必须写进结果文件，并且按
   §2 的方式记 sha256 —— 两个三元格式必须打**同一串 token id**，否则差异里混进了分词差异。
3. **报告口径**：非重叠窗口、逐窗口 PPL，报均值 ± 标准差；只报合并后的 NLL 会让长尾窗口被掩盖。

### 7.4 一条警告

用外部框架（HF / torch）读 GGUF 算出来的 PPL，量的是**那个框架的反量化实现**，不是本引擎的算子路径。
它可以用来判断"三元编码本身损失了多少"，但**不能**用来替代本引擎的 PPL，也不能与本引擎的吞吐读数拼接
成一句结论。
