# 基准测试：Ternary Bonsai 2 27B 在 RTX 4090 上的吞吐

本文是**两次完整跑分**（`just bench <制品> all`，两个三元制品各 20 条用例）的记录：读数、口径、环境，
以及这些数字**能**用来下什么结论、**不能**用来下什么结论。

**本文不含困惑度（Perplexity）。** 这一项的位置已经在 §7 预留：引擎目前没有能产出 PPL 的通路，
硬凑一个数只会误导。那一节写清楚了缺什么、以什么口径补。

有一处读数必须写在最前面：PQ2_0 的 `pp+tg` 用例里，prefill 在约 230–320 t/s 与约 838 t/s 两个档位之间跳，
同一进程内逐次变化（§6.2）。因此本文**不给出**那几行 prefill 的均值结论。第二轮实验已经把它的边界查清楚
（§6.5）：**不是频率、不是 MMA/SIMT 开关、不是分块**，但**需要** CUDA Graph、单块 prefill 与请求里带 decode，
而且在 20 次重复里只出现 5 次。

## 1. 结论摘要

本机（RTX 4090 24 GB / 驱动 615.71.09 / CUDA 13.3），两个三元制品各 20 条用例、每条 5 次重复：

| 维度 | 结果 | 出处 |
|---|---|---|
| prefill（只取 `pp` 用例）| PQ2_0 **250.9 – 274.0 t/s**；PTQ1_0 **42.9 – 50.8 t/s** | §5.1 §5.2 |
| prefill（`pp+tg` 用例）| PQ2_0 **不可用**：逐次在 ~230–320 与 ~838 t/s 两档间跳，均值无意义 | §6.2 |
| decode | PQ2_0 **41.9 – 55.9 t/s**；PTQ1_0 **15.9 – 16.4 t/s** | §5.1 §5.2 |
| CUDA Graph | 关图后 PQ2_0 decode 48.0 → **21.4 t/s**、PTQ1_0 16.3 → **4.6 t/s**；prefill 不变 | §5.1 §5.2 |
| KV 精度/编码 | 六种 KV 格式对 decode 的影响在 ±25% 内；KV 载荷 8.5 – 41.9 MB（ctx 640）| §5.1 |
| MTP 投机 | 两个格式都**没有收益**：PQ2_0 off 47.3 → draft4 45.0 t/s，接受率 32.6% | §5.1 §5.2 |
| 显存 | 权重上传 PQ2_0 7.19 GB / PTQ1_0 5.93 GB；KV 载荷随上下文线性 | §5.4 |
| 跨格式 | PTQ1_0 的 prefill 是 PQ2_0 的 **~0.18**，decode 是 **~0.3**，换来省 1.26 GB 显存 | §5.3 |
| 跨运行 | PTQ1_0 两次跑分逐条吻合在 2% 内；PQ2_0 稳定的那几列在 7% 内，带档位的列差 20% – 60% | §6.6 |

一句话：**PQ2_0 的 decode 约 45 t/s、prefill 约 260 t/s（`pp` 口径，慢档）是本机能站住的量级；小数点后的
位数在本机上没有意义。要吞吐选 PQ2_0，PTQ1_0 买到的是更小的盘上体积与显存。**

## 3. 口径：这些数分别是什么

### 3.1 三个 test kind 的计时边界

`ninfer_bench` 走的是**产品路径**：`Engine::prepare_tokens()` + `Engine::generate()`，没有私有的
prefill/decode 循环。三种 kind 的定义（沿用上游 `bench/README.md`）：

| kind | 做什么 | 报什么 |
|---|---|---|
| `pp{P}` | 准备 `P` 个 token，只请求 1 个输出 token | prefill t/s = `P / GenerationTimings.prefill_seconds` |
| `tg{G}` | 在计时区间外准备 1 个 token 的种子，请求 `G+1` 个输出 token | 计入 decode 的正好是 `G` 个 token |
| `pp{P}+tg{G}` | 先 `P` token prefill，再按同样约定生成 `G+1` | 同一次生成里的两段速率 |

所有请求都用 raw 输出、关掉模型自带的停止条件、关掉前缀复用（`ninfer_bench.cpp` 里
`execution.allow_prefix_reuse = false`）—— 目的是让"请求了多少 token"是精确的，而不是再引入一条生成路径。

### 3.2 被钉死的量

`tools/bench/bench.sh` 把这些值固定下来，手敲很容易漏：`-r 5`（5 次重复）、`--warmup 1`（1 次预热，
不计入）、`--prefill-chunk 1024`、语料同上、CUDA Graph 默认开（`graph-off` 那条用例显式关）。
`max_context` 由每条用例的 token 数自动定容，表里逐行给出。

### 3.3 表里的数是什么统计量

**5 次重复的均值 ± 样本标准差**，`rsd` 列 = 标准差 / 均值。`rsd` 大（> 10%）的行请按 §6 的方式理解：
它们描述量级，不描述可复现的精确值。§6 的所有结论都另外取了逐次数据（`-o json` 的 `reps[]`）后才下。

### 3.4 四个容易读错的地方

1. **`pp512` 与 `pp512+tg128` 的 prefill 不是同一个量。** 前者只请求 1 个 token，后者后面还跟着 decode，
   两段都参与同一次生成的墙钟，而且后者的 prefill 还会落到快档（§6.5）。跨表比较时不要把它们当成同一个数。
2. **`pp+tg` 的 prefill 列在 PQ2_0 上有档位问题**（§6.2），只有 `pp` 列的 prefill 与所有 decode 列可用。
3. **`decode_output_tok_s` 与 `decode_engine_tok_s` 在两次运行里逐行相同**（含 MTP 三条）。上游文档说后者
   会带上最后未提交的投机轮工作，本机这一版读数里没有体现出来，照抄 CSV 即可，不要按上游文档想当然。
4. **进程内的历史会影响读数。** 同一条 `-pg 512,128` 在本文里出现 8 次（两个制品各 4 次），给出 8 个不同的
   prefill 数，原因见 §6。

## 4. 复现

```bash
# 需要 NINFER_ROOT=<ninfer 源码树>（同时用来定位语料）与 ninfer_bench 构建
just build-bench
just bench /data/Ternary-Bonsai-2-27B-ninfer/Ternary-Bonsai-2-27B-PQ2_0.ninfer all
```

`ninfer_bench` 由 `just build-bench` 构建（`-DNINFER_BUILD_BENCHMARKS=ON`）。输出目录：

```text
out/bench-<制品名>-<UTC 时间戳>/
  manifest.txt            环境与输入摘要（§2 的表就来自这里）
  results.csv             全部用例的 tidy CSV，首两列是 case,suite
  all__<case>.csv         单次 ninfer_bench 的原始 CSV
```

要复现 §6 的档位结论，直接跑逐次 JSON（不需要 bench.sh）：

```bash
ninfer_bench --weights <制品> --corpus <语料> -pg 512,128 -r 20 --warmup 3 \
  --prefill-chunk 1024 -o json --output-file /tmp/reps.json
# 逐次速率 = n_prompt / reps[i].timings.prefill_seconds
```

`out/` 是**证据目录**：脚本不写进制品目录，`just clean` 也刻意不删它。

‡ 标记的 prefill 读数落在 §6.2 的档位问题里，**不要引用其均值**；同一行的 decode 读数不受影响。

三类可用读数的解读：

- **prefill 随长度平坦**（250.9 / 264.1 / 268.7 t/s，512 / 2048 / 8192 token）。`pp512` 略低是它每次只请求
  1 个 token、单次生成的固定开销占比更大。 `rsd` ≤ 6%，是本文最稳的 prefill 结论。
- **CUDA Graph 只对 decode 有意义**：开图 48.0 t/s、关图 21.4 t/s（同一 `-pg 512,128`，`rsd` 均 ≤ 9%），
  prefill 两行 272.4 对 267.1 在噪声内相同。原因是 decode 每步只发一次小规模 kernel 序列，发射开销
  占比高；prefill 本来就长。
- **MTP 在 bench 口径下没有收益**：只比 decode 列，off 47.3 → draft4 45.0 t/s，接受率 32.6%。这与 CLI
  贪心口径的 74% 接受率不矛盾 —— 基准自己采样，且把草稿开销算进墙钟。`draft8` 那条显式关图是
  **规避上游缺陷**（草稿窗口 ≥ 8 时 CUDA Graph 的 exec update 会失败，官方非三元制品同样复现），
  它量的是缺陷，不是投机。

## 6. 噪声与档位：同样的命令为什么给出不同的数

这是本次跑分最值得记下来的一条，因为它决定了本文之外的所有对比应该有多保守。第二轮的归因实验把它的
边界查得比较清楚了：**不是硬件状态，是 prefill 的软件路径在选择，而选择条件还不完全明确**。

### 6.1 证据一：同一个工作负载的八个读数

`-pg 512,128`（prefill 512 + 生成 128）在本文出现八次，参数只差自动定容的 `max_context`，prefill 的
计算量完全相同：

| 出现位置 | 制品 | max ctx | prefill t/s | rsd |
|---|---|---|---|---|
| `panel` | PQ2_0 | 2048 | 295.3 ± 34.6 | 12% |
| `kv-bf16` | PQ2_0 | 640 | 316.6 ± 147.6 | 47% |
| `mtp-off` | PQ2_0 | 640 | 497.9 ± 310.8 | 62% |
| `graph-on` | PQ2_0 | 640 | 272.4 ± 94.3 | 35% |
| `panel` | PTQ1_0 | 2048 | 44.2 ± 0.6 | 1% |
| `kv-bf16` | PTQ1_0 | 640 | 43.6 ± 0.6 | 1% |
| `mtp-off` | PTQ1_0 | 640 | 42.2 ± 0.5 | 1% |
| `graph-on` | PTQ1_0 | 640 | 44.2 ± 0.4 | 1% |

PQ2_0 的最高与最低相差 **1.8 倍**（均值口径），PTQ1_0 只差 5%。同一台机器、同一个二进制、同一份语料。

### 6.2 证据二：逐次重复的读数显示两个档位

`results.csv` 只给均值，所以另跑了逐次数据（`-o json` 的 `reps[]`，把每次重复的 `prefill_seconds` 换算
成 t/s）。PQ2_0，`-pg 512,128 -r 20 --warmup 3 --prefill-chunk 1024`：

```text
prefill t/s 逐次：
  308 284 247 280 312 280 244 249 229 245 225 838 684 838 264 267 838 302 320 838
  mean=404.5  median=282.3  min=224.5  max=837.7  std=241.8   （20 次里 5 次落在快档）
decode t/s 逐次：
   47  48  46  44  42  44  44  43  42  43  44  44  42  41  43  42  42  42  41  45
  mean= 43.6  median= 43.5  min= 41.3  max= 48.5  std=  1.9
```

同一个进程里，prefill 会在两个档位之间跳：

- **快档 ≈ 838 t/s**，而且常常**重复到小数点后两位**（早先一次运行里连续三次是 837.4 / 837.6 / 837.6）。
  纯计算决定的量才会这样重现。
- **慢档 ≈ 230 – 320 t/s**，`rsd` 明显更大（±12%）。
- **decode 完全不受影响**：20 次里 41.3 – 48.5，快档那 5 次的 decode 与慢档的没有区别。所以这不是"整卡快慢"，
  也不是访存或供电的波动，而是 prefill 这一段特有的现象。

对照：PTQ1_0 同样的 `-pg 512,128`（§5.2 的四行）`rsd` ≤ 1%，没有档位。

### 6.3 证据三：不是 GPU 频率（100 ms 采样对齐实测）

把 100 ms 的 `nvidia-smi` 采样与逐次重复按 `load_seconds` + 每次 `total_seconds` 对齐，20 次重复的
SM 频率与功耗如下（同一轮 `-pg 512,128 -r 20 --warmup 0`，无预热以便对齐）：

| # | prefill t/s | decode t/s | SM MHz（中位/最小/最大）| 功耗 W 中位 |
|---|---|---|---|---|
| 1 | 325 | 57.7 | 2745 / 2745 / 2745 | 121 |
| 5 | **838** | 46.3 | 2730 / 2730 / 2730 | 297 |
| 10 | 226 | 43.3 | 2730 / 2715 / 2730 | 262 |
| 12 | **837** | 43.3 | 2730 / 2715 / 2730 | 289 |
| 17 | **837** | 44.4 | 2730 / 2730 / 2730 | 310 |
| 20 | 232 | 42.7 | 2730 / 2715 / 2730 | 321 |

全部 20 次重复里 SM 频率都在 **2715 – 2745 MHz**（典型 2730），快档与慢档之间没有差别。
**3.6 倍的速率差不可能来自频率**，何况功耗也都在同一区间。

### 6.4 证据四：触发条件矩阵

用同一台机器上的定向实验逐条排除（全部 `-pg 512,128`，除注明外 chunk 1024、CUDA Graph 开、MMA 默认开）：

| 改动 | 逐次 prefill t/s | 快档出现 |
|---|---|---|
| 默认 | 225 – 320 与 **838**（20 次里 5 次）| **是** |
| `NINFER_TERNARY_MMA=0`（强制 SIMT）| 49.5 – 54.4（8 次）| 否 |
| `NINFER_TERNARY_MMA=1`（显式开）| 247 – 837（8 次里 3 次）| 是 |
| `--no-cuda-graph` | 158 – 316（8 次）| 否 |
| `--prefill-chunk 128` | 233 – 259（8 次）| 否 |
| `--prefill-chunk 512` | 233 – 806（8 次里 2 次）| 是 |
| `--prefill-chunk 2048` | 231 – 610（8 次里 1 次）| 是 |
| `-pg 1024,128`（prompt 1024）| 264 – 320（8 次）| 否 |
| `-pg 2048,128`（prompt 2048）| 274 – 317（8 次）| 否 |
| `-pg 512,8`（decode 只有 8 token）| 239 – 304（20 次）| 否 |
| `-p 512`（请求里没有 decode）| 127 – 396（20 次）| 否 |
| `-n 128`（只有 decode）| decode 39.6 – 45.3（20 次）| — |

读出来的条件：**要落到快档，需要同时满足 CUDA Graph 开、张量核路径开（`MMA=0` 时稳定在 52 t/s，
不存在这个档位）、prefill 单块（chunk 128 时消失）、prompt 恰好 512 token（1024 / 2048 都没有出现）、
并且同一次请求里带 ≥128 token 的 decode**。即使全部满足，20 次里也只出现 5 次。

被排除的解释：

| 假设 | 判定 | 依据 |
|---|---|---|
| GPU 频率 / 功耗墙 | **排除** | §6.3：快慢两档的 SM 频率同为 2730 MHz |
| MMA / SIMT 路径切换 | **排除** | `MMA=0` 是均匀的 52 t/s，两档都在 MMA 开的那一侧 |
| 只是"没预热"| **排除** | 无预热的 20 次里，第 1 次 325 t/s、第 5 次 838 t/s、第 6 次 430 t/s，顺序无关 |
| 前缀复用（少算工作量）| **源码层面排除** | `ninfer_bench.cpp` 设了 `allow_prefix_reuse = false` |
| 分块数变化 | **不成立** | chunk 128 会消灭快档，但 chunk 512 / 2048 都保留它 |

### 6.5 还没解释的部分，与怎么把它做完

剩下的问题是：**同一个进程里，是什么让某几次重复走了快档**。目前只能确定它是 prefill 的软件路径选择，
而且与请求里是否有 decode 有关。把它钉死需要引擎内部的观测，两条路：

```bash
# 1. 用 bench 自带的 profiler 边界，对一次测量重复做 Nsight Systems 采集，比较快慢两档的 kernel 序列
ninfer_bench --weights <制品> --corpus <语料> -pg 512,128 -r 1 --warmup 0 \
  --prefill-chunk 1024 --profile-measured
# 2. 在 prefill 分发处加一条日志（形状 + 选中的实现），跑 20 次看哪条路径对应 838 t/s
```

在这之前，正确的引用方式是**引用中位数**（约 282 t/s）而不是均值，并且知道快档（约 838 t/s）是真实存在的
——它是一条稳定的计算路径（重复到小数点后两位），只是引擎目前只在少数重复里走到它。

### 6.6 跨运行对照

同一台机器、同一个 `ninfer_bench` 二进制、同一份语料、同一条命令，三次运行（`tools/bench/README.md` 记的
那次、9-22、9-23；前两次驱动 610.57.04，本次 615.71.09）：

| 用例 | 更早一次 | 9-22 | 9-23（本文）| 极差 |
|---|---|---|---|---|
| PQ2_0 panel pp512 | 267.2 ± 18.4 | 260.5 ± 16.2 | 263.4 ± 34.5 | 2.5% |
| PQ2_0 panel pp2048 | 303.4 ± 5.6 | 291.8 ± 6.7 | 274.0 ± 18.3 | **9.7%** |
| PQ2_0 panel tg128 | 50.8 ± 4.3 | 49.9 ± 11.3 | 51.3 ± 4.9 | 2.7% |
| PQ2_0 decode tg512 | – | 41.8 ± 1.8 | 41.9 ± 1.6 | 0.2% |
| PQ2_0 kv bf16 prefill ‡ | 427 | 691.0 | 316.6 | **118%** |
| PQ2_0 mtp off prefill ‡ | 450 | 344.6 | 497.9 | **44%** |
| PQ2_0 graph off decode | 24.2 | 22.1 | 21.4 | **13%** |
| PTQ1_0 panel pp512 | – | 43.9 ± 0.6 | 44.5 ± 0.8 | 1.4% |
| PTQ1_0 prefill pp8192 | – | 49.3 ± 0.2 | 50.3 ± 0.2 | 2.0% |
| PTQ1_0 decode tg512 | – | 16.4 ± 0.0 | 16.3 ± 0.1 | 0.6% |

读法：**PTQ1_0 的每一列都在 2% 内复现；PQ2_0 里 `rsd` 小的列在 3% 内复现，`rsd` 大的列（标 ‡）差 44% – 118%。**
"跑得快不快"看前一类，"跑得多快"不要看后一类。

### 6.7 结论与操作建议

- 本文件的表格里，`rsd` ≤ 10% 且不带 ‡ 的行可以当作同一台机器上的稳定读数；带 ‡ 的行只应当作量级，
  引用时用中位数（§6.5）。
- 跨机器、跨驱动、跨时段、跨 suite 顺序的比较，在**没有锁频、没有固定预热**的前提下不可靠。
- 想让某个数变成可引用的结论：单独跑一条用例、`-r` 提到 10 以上、`--warmup` 提到 2 以上、存 `-o json`
  并用逐次数据而不是均值，同时把 GPU 状态（时钟/温度/功耗）一起记下来。

## 7. 困惑度（Perplexity）：待测

**本节的表全部是空的，这不是"未通过"，而是"还没测"。** 位置在这里预留，补上时不需要改动其它章节。

### 7.1 现在为什么是空的

| 事实 | 依据 |
|---|---|
| 本移植的验收判据是"逐字节一致 + 吞吐"，不含困惑度 | 移植报告、本文 §5 |
| `ninfer_bench` 只测吞吐，不产出任何似然量 | 上游 `bench/README.md`；本文引用的 CSV 列里没有 NLL/logits |
| 上游 `eval/` 是能力套件（AIME / GPQA / needle-in-haystack），不是 PPL | `eval/configs/*.yaml` |
| 公开路径 `Engine::generate()` 只回 token id，不回逐 token logprob | 引擎头文件；`ninfer-serve` 未开 `logprobs` |

### 7.2 补上它需要什么

1. **一条只读的似然通路**：给定一段 token id，返回每个位置的负对数似然（NLL）。最自然的位置是
   `Engine` 上加一个 `score_tokens()`（复用现有的前向与 KV 布局，不新建生成路径），或在
   `ninfer-serve` 上开 `logprobs` 再写一个打分脚本。二者都要保证打分走的是与生成完全相同的算子路径，
   否则量到的是另一套东西。
2. **钉死语料与 tokenizer**：数据集、分词器、是否加 BOS、窗口边界必须写进结果文件，并且按
   §2 的方式记 sha256 —— 两个三元格式必须打**同一串 token id**，否则差异里混进了分词差异。
3. **报告口径**：非重叠窗口、逐窗口 PPL，报均值 ± 标准差；只报合并后的 NLL 会让长尾窗口被掩盖。

### 7.4 一条警告

用外部框架（HF / torch）读 GGUF 算出来的 PPL，量的是**那个框架的反量化实现**，不是本引擎的算子路径。
它可以用来判断"三元编码本身损失了多少"，但**不能**用来替代本引擎的 PPL，也不能与本引擎的吞吐读数拼接
成一句结论。
